# 超时、重试、异常与幂等

目标：让 Dubbo 调用失败时行为可预期，避免一次网络抖动变成重复扣款或雪崩。

## 1. 超时不是“服务一定没执行”

Consumer 等待 1 秒后超时，可能有多种情况：

```text
请求没到 Provider
Provider 收到但还没开始执行
Provider 已执行成功，但响应在网络中丢失或返回太慢
```

所以“超时后再试一次”可能造成写操作执行两次。

## 2. 为接口设置合理超时

```java
@DubboReference(timeout = 1000)
private UserService userService;
```

超时时间应来自实际监控数据，而不是随手写一个很大的数：

- 查询类接口通常较短。
- 调用外部系统或执行复杂计算的接口可能更长。
- 超时预算要覆盖网络、排队和服务执行时间。

不要无限增大超时来“解决”错误。超时过大只会让线程堆积，故障时更难恢复。

## 3. 重试只适合幂等操作

读取用户资料通常可以重试：

```java
@DubboReference(timeout = 1000, retries = 1)
private UserService userService;
```

`retries = 1` 表示首次失败后最多额外重试一次，总调用次数最多两次。

创建订单、扣减库存、扣款等写操作默认不要盲目重试。若业务需要重试，必须提供幂等键，例如 `requestId`，Provider 用数据库唯一约束或幂等记录保证同一请求只生效一次。

## 4. 统一业务异常

接口应定义可识别的业务异常：

```java
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(Long userId) {
        super("用户不存在：" + userId);
    }
}
```

Consumer 可以根据业务异常返回明确提示；网络异常、超时、序列化异常则应记录调用上下文并按降级策略处理。

不要把数据库连接异常、内部堆栈或密码等敏感信息原样透传给 Consumer。

## 5. 降级不是返回假成功

当用户服务不可用时，订单服务可以：

- 对非关键展示信息返回默认昵称。
- 对必须依赖用户状态的下单操作明确失败或稍后重试。
- 记录调用失败指标并触发告警。

不能为了让接口“看起来成功”而伪造库存、支付、权限等关键结果。

记住这条原则：RPC 写操作要以幂等为前提，再讨论重试。
