# 注册中心与负载均衡

目标：理解 Provider 和 Consumer 为什么不需要互相写死 IP，以及多个 Provider 如何分担调用。

## 1. 注册中心做了什么

Provider 启动后向 ZooKeeper 注册自己的服务地址：

```text
UserService -> 10.0.0.11:20880
UserService -> 10.0.0.12:20880
```

Consumer 订阅这个服务。ZooKeeper 中的地址发生变化时，Consumer 会收到通知并更新本地可调用列表。

因此 Consumer 配置的是“我要调用哪个接口”，而不是“我要调用哪台服务器”。

## 2. 启动两个 Provider

本地可复制 `user-provider` 的启动配置，分别设置不同应用名和 Dubbo 协议端口：

```yaml
dubbo:
  application:
    name: user-provider-a
  protocol:
    port: 20880
```

第二个实例：

```yaml
dubbo:
  application:
    name: user-provider-b
  protocol:
    port: 20881
```

两个实例都实现 `UserService`，并注册到同一个 ZooKeeper。Consumer 就能发现两个地址。

## 3. 负载均衡

同一个接口有多个 Provider 时，Consumer 会在调用前选择一个。常见策略：

| 策略 | 适用说明 |
|---|---|
| 随机 | 默认思路，实例能力接近时适用 |
| 轮询 | 让请求按顺序分配 |
| 最少活跃调用 | 单次调用耗时差异明显时较有帮助 |
| 一致性哈希 | 希望同一参数尽量落到同一实例时使用 |

配置示例：

```java
@DubboReference(loadbalance = "roundrobin")
private UserService userService;
```

不要只因为“轮询容易理解”就固定使用它。真实选择要结合实例配置、请求耗时、连接数和业务是否需要粘性。

## 4. 注册中心不可用时会怎样

已经启动并拿到 Provider 地址的 Consumer 通常仍可调用现有 Provider；但新实例注册、地址变更和故障发现会受到影响。

因此生产环境的注册中心要做高可用，而不是单点部署。Consumer、Provider、ZooKeeper 的监控和告警应作为同一条依赖链来看待。
