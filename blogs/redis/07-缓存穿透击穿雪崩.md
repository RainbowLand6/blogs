# 缓存穿透、击穿与雪崩

这三个词很像，但问题不同。先用一句话区分：

| 问题 | 发生了什么 |
|---|---|
| 缓存穿透 | 请求的数据根本不存在 |
| 缓存击穿 | 一个热点 Key 刚好失效 |
| 缓存雪崩 | 大量 Key 在同一时间失效或 Redis 整体不可用 |

## 1. 缓存穿透

攻击者或异常客户端不断请求不存在的 `product:-1`。Redis 没有，数据库也没有，每个请求都打到数据库。

基础解决方案：

- 缓存空值，且使用较短 TTL。
- 对 ID 做格式和范围校验。
- 数据量很大时可考虑布隆过滤器。

## 2. 缓存击穿

热门商品 `product:1001` 刚过期，大量并发请求同时发现未命中，于是一起查数据库。

基础解决方案是互斥回填：只有一个请求去查数据库和重建缓存，其他请求短暂等待或稍后重试。

伪代码：

```text
缓存未命中
  -> 尝试获取 product:1001:lock
  -> 获取成功：再次检查缓存，查库并回填，释放锁
  -> 获取失败：短暂等待后重试读缓存
```

锁实现细节见下一篇。热点非常高时也可以使用逻辑过期和异步刷新，但复杂度更高。

## 3. 缓存雪崩

例如凌晨统一写入的十万条缓存都设置 3600 秒过期，1 小时后同时失效，数据库会被瞬时流量压垮。

基础解决方案：

```java
int ttl = 3600 + ThreadLocalRandom.current().nextInt(0, 300);
jedis.setex(key, ttl, value);
```

也就是在基础 TTL 上加随机值，打散过期时间。

还应准备：

- Redis 高可用与监控。
- 接口限流、降级、熔断。
- 数据库自身的容量保护。

## 4. 不要一上来就做复杂方案

对于普通后台系统，先做到“合理 TTL + 缓存空值 + 删除缓存 + 监控命中率和内存”已经解决了大部分问题。逻辑过期、布隆过滤器和多级缓存应该由真实流量与故障数据推动。
