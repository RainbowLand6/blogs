# 什么是 Kafka

Kafka 是一个用于传递消息的系统。一个程序把消息写进去，另一个或多个程序稍后读出来处理。

拿电商下单举例：用户支付成功后，订单服务不必亲自做库存扣减、发优惠券、发通知。它只需要发送一条“订单已支付”消息；库存、营销、通知等服务各自订阅并处理。这种方式让服务之间不必互相等待。

```text
订单服务 --发送--> Kafka Topic --消费--> 库存服务
                                  └------> 通知服务
                                  └------> 数据分析服务
```

## 为什么不用直接调用接口

直接调用看起来简单，但下游服务一多，订单服务会变成“总调度员”：

- 下游服务变慢，订单接口也可能变慢。
- 某个下游暂时不可用，订单是否应该失败很难决定。
- 新增一个处理步骤时，要修改订单服务。

Kafka 把“发送消息”和“处理消息”分开。发送方只负责把事实写入 Kafka；接收方按自己的速度处理。

## 先认识六个词

| 名词 | 小白解释 | 例子 |
|---|---|---|
| Broker | Kafka 的一台服务节点 | 一台运行 Kafka 的服务器 |
| Topic | 消息分类，相当于一个主题频道 | `order-paid` |
| Message / Record | 一条具体消息 | “订单 1001 已支付” |
| Partition | Topic 的分区，消息的实际存放单位 | `order-paid-0` |
| Producer | 发送消息的程序 | 订单服务 |
| Consumer | 读取消息的程序 | 库存服务 |
| Consumer Group | 一组协作消费的消费者 | 多台库存服务实例 |

## Kafka 的两个重要特点

### 消息会保留一段时间

消费者读完消息后，Kafka 通常不会立刻删除它。消息会按 Topic 的保留策略保存，例如 7 天。

因此，新的消费者可以从旧消息开始补数据；消费程序出错重启后，也可以从上次位置继续。

### 同一个 Topic 可以被多个业务独立消费

库存服务和通知服务使用不同的消费者组。它们各自拥有消费进度，互不影响。

```text
Topic: order-paid
├── 库存组：已处理到第 100 条
└── 通知组：已处理到第 80 条
```

## Kafka 不适合做什么

- 不要把它当数据库：它擅长追加消息，不擅长按任意条件查询。
- 不要把超大文件直接塞进去：文件放对象存储，Kafka 传文件地址和元数据。
- 不要把“发到 Kafka”理解成“业务一定完成”：消费者是否成功处理，是后面的另一件事。

## 本篇小结

Kafka 的核心作用是：让一个系统可靠地通知其他系统发生了什么。下一篇先不讲复杂概念，直接在本地启动 Kafka，亲手发送第一条消息。
