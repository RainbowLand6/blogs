# 消息可靠性与幂等消费

目标：知道“消息不丢”和“业务不重复”分别靠什么保证。

## 1. 先接受一个事实：业务通常是至少一次消费

消费者按“处理成功后再提交位移”的顺序工作。若业务已成功、但提交位移前程序崩溃，重启后 Kafka 会再次投递该消息。

这不是 Kafka 出错，而是为了尽量避免丢消息。因此，消费者要能安全地处理重复消息，也就是具备幂等性。

## 2. 生产者的基础可靠配置

```java
properties.put(ProducerConfig.ACKS_CONFIG, "all");
properties.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
properties.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
properties.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 120_000);
```

含义：

| 配置 | 作用 |
|---|---|
| `acks=all` | 所有同步副本确认后才算成功，单机学习环境例外 |
| `enable.idempotence=true` | 生产者重试时避免写入重复记录 |
| `retries` | 临时网络错误时允许重试 |
| `delivery.timeout.ms` | 到达总超时时间后明确返回失败 |

生产者幂等只解决“同一生产者重试造成的 Kafka 记录重复”，不能替代消费者的业务幂等。

## 3. 消费者的幂等做法

以“给订单发优惠券”为例，给每条事件一个唯一 `eventId`：

```json
{
  "eventId": "8ba89c26-41b3-4d40-a9f4-4a4a5c0b0b11",
  "orderId": "order-1001",
  "type": "ORDER_PAID"
}
```

消费时把 `eventId` 写入数据库，并对它建立唯一索引：

```sql
CREATE TABLE consumed_event (
    event_id VARCHAR(64) PRIMARY KEY,
    consumed_at TIMESTAMP NOT NULL
);
```

业务处理时：

1. 尝试插入 `event_id`。
2. 插入成功，说明第一次处理，再发优惠券。
3. 主键冲突，说明已处理过，直接跳过。
4. 业务成功后提交 Kafka 位移。

最好把“记录已消费事件”和“真正的业务写库”放在同一个数据库事务中，否则仍可能出现中间状态。

## 4. 失败消息不要无限重试

遇到参数错误、数据格式错误等永久性失败，原地无限重试只会卡住分区。常见策略是：

```text
第一次失败 -> 短暂重试
多次失败 -> 发送到死信 Topic（DLQ）
人工或定时任务修复 -> 再次投递
```

死信 Topic 命名可以是 `order-paid-dlq`。写入死信时，要带上原 Topic、分区、位移、异常信息，方便定位。

## 5. 一条实用原则

不要试图用一句“Kafka 保证不重复”解决所有问题。可靠消息链路至少要同时考虑：

- 生产者是否确认写入。
- 消费者是否在业务成功后提交位移。
- 业务是否能抵抗重复投递。
- 失败消息是否可观察、可恢复。
