# 消费者组与并发消费

目标：分清“多台服务分担工作”和“多个业务都收到消息”这两种需求。

## 1. 同组消费者会分摊消息

假设 `order-paid` 有 3 个分区，库存服务启动 3 个实例，且它们的 `group.id` 都是 `inventory-group`：

```text
Partition 0 -> 库存实例 A
Partition 1 -> 库存实例 B
Partition 2 -> 库存实例 C
```

同一条消息只会被这个组中的一个实例处理。这适用于扩容处理能力。

## 2. 不同组各自消费一份

```text
Topic: order-paid
├── inventory-group -> 扣库存
├── notification-group -> 发送通知
└── analytics-group -> 数据分析
```

每个组都有独立位移，因此三个业务都会收到同一条订单消息。

## 3. 代码无需大改

第 5 篇消费者代码已经支持消费者组。要模拟两个库存实例，只需要同时运行两个程序，并把它们的 `GROUP_ID_CONFIG` 都设为：

```java
properties.put(ConsumerConfig.GROUP_ID_CONFIG, "inventory-group");
```

然后发送多条消息。观察两个控制台，可以看到它们分摊处理消息。

> 如果 Topic 只有 1 个分区，即使启动两个同组消费者，也只有一个会真正收到消息。另一个处于空闲状态，这是正常现象。

## 4. Rebalance 是什么

消费者实例加入、退出，或分区数量变化时，Kafka 会重新分配“哪个消费者处理哪个分区”，这个过程叫 Rebalance（再均衡）。

在再均衡的短暂期间，消费会暂停。因此不要频繁重启消费者，也不要让单次消息处理时间远超过 `max.poll.interval.ms`，否则 Kafka 可能误判消费者失联并触发再均衡。

## 5. 如何为业务命名消费者组

消费者组名应该表达“谁在处理这类消息”，例如：

```text
inventory-service
coupon-service
order-data-sync
```

不要把环境、实例编号混进组名，例如不要给每台机器写成 `inventory-01`、`inventory-02`。这样会把原本应分担工作的实例拆成多个组，导致每台机器都重复消费。
